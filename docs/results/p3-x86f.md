## Selected policies

The parent selected these policies from the x86f fleet runs.
The composite still requires its own fleet A/B against `2afc101`.

| Model | Composite `auto` policy | Reference |
|---|---|---|
| Sapphire Rapids | `straight_1k`, short-first inline copy, medium chunks | chunks |
| Granite Rapids | `straight_1k`, medium entry, shared copy/move pairs, medium chunks | pairs and chunks |
| Zen 4 | `tiered`, unchanged NT threshold of 12 MiB + 1 byte | baseline |
| Zen 5 | `compact`, forward-source threshold of 64 KiB, NT threshold of 32 MiB | source64 and temporal |

The parent rejected the Zen 4 byte-move candidate and the dispatch64 candidate.
The ABI dispatch boundary remains 128 bytes.
The temporal experiment still selects its original NT threshold of 64 MiB + 1 byte.
The x86f experiment flags now inherit the composite defaults on other paths.
Historical comparisons therefore use the frozen binaries, not these flags on the new source.

Zen 5 uses temporal stores for the 16 MiB copy cases and retains NT stores at 64 MiB.
The 32 MiB transition is an interpolated choice, not a measured threshold winner.
Zen 4 retains its previous threshold.

### Granite Rapids composition

Copy and move paths at every length from 0 through 64 have identical executed instruction bytes to the measured pairs binary.
Set paths at every length from 0 through 1024 have identical executed instruction bytes to the measured chunks binary.
The complete set function matches after branch-target normalization, but its raw bytes differ.
All three complete large kernels match both measured references byte for byte.

Medium copy and move paths do not match the measured chunks bytes.
The differences at every length from 65 through 1024 are:

- The return-register copy moves from the end to the start.
- Stores use `%rax`, which holds `%rdi`, as their destination base.
- The entry takes one additional branch.
- The move entry uses `n > 63` instead of `n >= 64`.

Normalization of these specific differences leaves no other instruction difference across all 1920 copy/move paths.
That comparison does not establish equal latency.
The extra taken branch is a concrete composite performance risk.

### Zen 5 composition

The complete composite `.text` differs from the measured source64 image in exactly six bytes.
Those bytes encode two NT comparisons, one in `copyLarge` and one in `largeKernel`.
Both comparisons change from `0xc00001` to `0x2000000`.
All other `.text` bytes match.
The 288-byte `forwardSource` function is unchanged.

The older one-MiB source candidate also differs in its forward-overlap threshold and predicate order.
It is not a byte-identical reference for the source64 policy.
Against pre-composite main, the composite changes the large copy/move paths and their relative transfers.
The set kernels retain their bytes.

## Local validation

The final combined gate passed 350/350 steps and 38/38 tests:

```sh
zig build test test-export test-dispatch codegen-x86 test-generic-set -j2 --summary all
```

`just test` also passed.
The gate resolves the experiment separately for each CPU.
It checks the actual AMD threshold comparisons and rejects mutations to their immediates.
The mutation suites passed 78 cases on each Intel model, 77 on Zen 4, and 78 on Zen 5.

ReleaseFast installs passed for all seven `bench.toml` rows.
Additional installs passed for `x86_64_v3` and AArch64 generic.
One QEMU guard run on `x86_64_v3` passed 28,047,836 cases through one MiB in 325 seconds.
The guard used a static musl build and `qemu-x86_64 -cpu max`.
It does not establish AVX-512 correctness.

Zig formatting and x86 lint passed.
Whole-source lint reports 18 existing diagnostics outside this change.
The parent still owns hardware correctness and composite performance acceptance.
