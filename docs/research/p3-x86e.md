## c8i: separate entry dispatch from block layout

The baseline tests the short class before the 64-byte boundary.
It then tests the 128-byte boundary on the medium path.
The earlier `medium_first` variant removes one medium predicate but adds one short predicate.
Its 64-byte entry alignment also differs from the baseline.

Candidate A preserves the initial size predicates and 16-byte entry alignment.
A branch hint makes the medium block follow the 64-byte decision directly.
The compiler reverses that decision's branch polarity.
Thus, A preserves the small decision tree, not every small block address or branch outcome.

Candidate B retains the leading `n >= 64` predicate from `medium_first`.
It retains 16-byte entry alignment instead of the earlier 64-byte alignment.
Both candidates retain the 1 KiB move class from main.

The local GNR benchmark places the entries at the same addresses in all three builds:

| Entry | Baseline | A | B |
|---|---|---|---|
| set | `0x1093450` | `0x1093450` | `0x1093450` |
| copy/move | `0x1093590` | `0x1093590` | `0x1093590` |

The following counts cover conditional branches from entry through the first destination store.
Each cell gives executed branches / taken branches.

| Operation and length | Baseline | A | B |
|---|---|---|---|
| copy/move, 1 | 3 / 1 | 3 / 1 | 4 / 2 |
| copy/move, 4 | 2 / 0 | 2 / 0 | 3 / 1 |
| copy/move, 17 | 2 / 1 | 2 / 2 | 2 / 2 |
| copy/move, 65 | 3 / 2 | 3 / 1 | 2 / 0 |
| copy/move, 129 | 4 / 3 | 4 / 2 | 3 / 1 |
| set, 65 | 3 / 2 | 3 / 1 | 2 / 0 |

The baseline copy/move first store for 65 bytes is at `0x1093649`.
A moves it to `0x10935e9`, while B moves it to `0x10935b0`.
A leaves the 4–15 byte copy/move instructions at their original addresses.
Other small blocks move, and the set zero-length branch changes encoding length.
The fleet must test those residual layout effects.

## GNR: preserve medium decisions, remove compact duplication

The base copy entry starts at `0x1093850` in `base/graniterapids/bin/bench-fastmem`.
Its leading decision tests the 64-byte boundary.
The 65-byte path uses two size predicates and two ZMM endpoint pairs.
The 192-byte path uses three predicates and four ZMM loads plus four stores.
These paths explain the medium-entry winner, not the small regression's exact cycle cost.

The short copy classes still use the compact four-transfer shape.
At 4–15 bytes, four dword loads precede four stores.
At 16–63 bytes, four XMM loads precede four stores.
Five scalar instructions calculate the compact offsets before those transfers.
Zero takes ten instructions through return, versus eight in the separate move entry at `0x10942a0`.

The pairs candidate retains the leading medium decision and the 16-byte ABI alignment.
Its copy classes use the existing move endpoint pairs below 64 bytes.
The candidate shares this body with move, so move block layout can also change.
The 65–256 transfer bodies and predicate counts remain unchanged.
The set candidate reverses the leading branch hint, so short sizes fall through.
The medium set path retains two predicates at 65 bytes, but gains a taken branch.
This is a layout tradeoff, not proof that medium parity survives.

The base set entry starts at `0x1093710`.
Zero takes eight instructions and three predicates.
The candidate changes its block layout rather than a zero-only predicate that taxes every medium call.

## Intel: duplicate traffic at 384 and 768 bytes

The SPR copy and move entries start at `0x1093880` and `0x10942c0`.
Both use the same medium transfer bodies.
No overlap-direction test executes at 384, 512, 768, or 1024 bytes.

| Length | Base loads/stores | Candidate loads/stores |
|---|---|---|
| 257–384 | 8 / 8 | 6 / 6 |
| 385–512 | 8 / 8 | 8 / 8 |
| 513–768 | 16 / 16 | 12 / 12 |
| 769–1024 | 16 / 16 | 16 / 16 |

The base 768-byte class transfers 1024 bytes through each side of the operation.
Its endpoints overlap by 256 bytes.
A misaligned 64-byte access also crosses cache-line boundaries.
The new classes reduce duplicate transfers without a loop or a direction test.
All loads still precede all stores.
The 16-register class remains available above 768 bytes.

The class split adds one predicate inside each affected outer class.
Thus 512-byte and 1024-byte copies do not lose transfers and can lose time from the extra decision.
Those rows require explicit fleet scrutiny.
The change does not establish a complete explanation for the 1024-byte misalignment gap.

The SPR set entry starts at `0x1093740` and delegates above 512 bytes.
The 1024-byte call reaches `x86_64.set.largeKernel` after thirteen entry instructions.
That kernel checks NT and REP thresholds before its temporal loop.
The candidate keeps set through 1024 bytes in straight-line high-register classes.
REP and NT thresholds, and every large transfer body, remain unchanged.

## Zen 4: compiler-rt scalar shape and byte dependencies

The base copy entry starts at `0x1094d90`.
Its 4-byte and 8-byte classes already execute fewer instructions than compiler-rt.
Instruction count alone does not explain the reported constant 0.54 ns gap.

The candidate adapts compiler-rt's disjoint 4–15-byte class from the pinned Zig source.
It uses four dword endpoints with alternating loads and stores.
The byte class also permits alternating transfers.
`THIRD_PARTY.md` names both compiler-rt source files and their MIT attribution.
The 17–63-byte copy classes remain pairs, unlike the rejected x86e compact-vector experiment.
At 16 bytes, the candidate uses two XMM endpoints instead of two qword endpoints.

The base move entry at `0x10956c0` performs three byte loads and three stores for one byte.
The candidate performs one load and one store for that length.
The zero path remains separate from non-null pointer conversion.
Two-byte and three-byte moves retain the snapshot-before-store contract.
Their extra one-byte decision is a regression risk.

The base set entry at `0x1094c50` reaches its one-byte store after five predicates.
It reaches 65 bytes after three predicates and 192 bytes after four.
The candidate moves medium dispatch first and moves the one-byte decision ahead of the scalar ladder.
This trades a shorter medium path against an additional decision on other short lengths.

## Baseline: two different costs inside 65–256

The base SSE2 copy stub starts at `0x1093f50` in `base/x86_64/bin/bench-fastmem`.
At 65–128 bytes, it performs eight XMM loads and eight stores.
Its complete path takes 26 instructions.
The target GNR path takes ten instructions with two ZMM loads and two stores.
The target Zen 4 and Zen 5 paths take twelve instructions.
These sizes never enter a dispatched level in the base build.

Above 128 bytes, the stub instead takes six instructions and an indirect jump.
The GNR bounded move entry at `0x1022900` takes twelve instructions at 192 bytes.
The corresponding Zen 4 and Zen 5 entries start at `0x10235d0` and `0x1024300`.
Both also take twelve instructions.
They contain one size predicate and the same four-vector transfer as the target kernels.
There is no repeated scalar ladder and no source loop at these sizes.

The combined stub and level cost is eighteen instructions for copy/move at 192 bytes.
That equals the AMD target instruction count, but includes an indirect transfer.
GNR's target entry takes sixteen instructions.
The corresponding set totals are fifteen instructions through dispatch, versus thirteen on GNR and fifteen on AMD.
Equal instruction counts do not imply equal branch or front-end cost.

The dispatch candidate lowers only the ABI stub limit to 64 bytes.
Its level entry contract becomes `n > small_max`, with hidden names ending in `_above_small`.
The fixed-size and runtime inline limits remain 128 bytes.
The resolver-trap test checks the selected ABI boundary independently.

The new level entry needs a 128-byte decision that the old bounded entry omits.
Thus the candidate can improve 65–128 bytes and regress 129–256 bytes.
This tradeoff requires a full tier comparison, not only the 96-byte row.

## Zen 5: the copy gap is stale, the 1 MiB overlap gap is real

The cited `bench-results/20260926T040226Z-final-standard/summary.json` does not support the remaining 1.15 large-copy ratio.
All twelve fixed copy rows above 16 KiB have fastmem/compiler-rt ratios between 0.943 and 1.007.
None has a confidence interval wholly above 1.01.
The scorecard table reports a 0.98 tier ratio, consistent with those rows.
The disjoint source policy therefore remains unchanged.

The same run reports `move/fwd-gap1/1048576` at 1.222, with interval `[1.188, 1.239]`.
The base large entry starts at `0x1095240`.
Its forward-overlap selector at `0x109543c` requires at least `0xc00001` bytes before `forwardSource`.
The 1 MiB case therefore uses the destination-aligned temporal loop.
That loop increments by `0x800` at `0x109572e`.
With gap one, its source loads cross cache-line boundaries.

Compiler-rt's forward loop increments by `0x200` at `0x10acef2` and uses aligned source loads.
Fastmem's existing `forwardSource` at `0x108f630` also uses aligned source loads and a 512-byte main iteration.
The source candidate lowers only the forward-overlap selector to 1048576 bytes.
The existing NT exclusion for overlaps and the 65536-byte disjoint selector remain unchanged.
The 64 MiB source-loop body is unchanged.
