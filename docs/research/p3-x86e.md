No fleet run or AWS launch occurred in this lane.

## c8i: separate entry dispatch from block layout

The baseline tests the short class before the 64-byte boundary.
It then tests the 128-byte boundary on the medium path.
The earlier `medium_first` variant removes one medium predicate but adds one short predicate.
Its 64-byte entry alignment also differs from the baseline.

Candidate A preserves the initial size predicates and 16-byte entry alignment.
A branch hint makes the medium block follow the 64-byte decision directly.
The compiler reverses that decision's branch polarity.
Thus, A preserves the small decision tree, not every small block address or branch outcome.

Candidate B retains the leading `n >= 64` predicate from `medium_first`.
It retains 16-byte entry alignment instead of the earlier 64-byte alignment.
Both candidates retain the 1 KiB move class from main.

The local GNR benchmark places the entries at the same addresses in all three builds:

| Entry | Baseline | A | B |
|---|---|---|---|
| set | `0x1093450` | `0x1093450` | `0x1093450` |
| copy/move | `0x1093590` | `0x1093590` | `0x1093590` |

The following counts cover conditional branches from entry through the first destination store.
Each cell gives executed branches / taken branches.

| Operation and length | Baseline | A | B |
|---|---|---|---|
| copy/move, 1 | 3 / 1 | 3 / 1 | 4 / 2 |
| copy/move, 4 | 2 / 0 | 2 / 0 | 3 / 1 |
| copy/move, 17 | 2 / 1 | 2 / 2 | 2 / 2 |
| copy/move, 65 | 3 / 2 | 3 / 1 | 2 / 0 |
| copy/move, 129 | 4 / 3 | 4 / 2 | 3 / 1 |
| set, 65 | 3 / 2 | 3 / 1 | 2 / 0 |

The baseline copy/move first store for 65 bytes is at `0x1093649`.
A moves it to `0x10935e9`, while B moves it to `0x10935b0`.
A leaves the 4–15 byte copy/move instructions at their original addresses.
Other small blocks move, and the set zero-length branch changes encoding length.
The fleet must test those residual layout effects.

## c7a: compiler-rt comparison

The baseline `znver4` benchmark contains these entries:

| Implementation | Symbol | Address |
|---|---|---|
| compiler-rt copy | `memcpy` | `0x10ac990` |
| compiler-rt move | `memmove` | `0x10ac530` |
| fastmem copy/move | `x86_64.move.kernel` | `0x1094ab0` |

Counts below include the first destination store and the final return.
They include entry instructions, but exclude the caller's call instruction.
Each cell gives first-store instruction / total instructions / conditional branches.

| Length | compiler-rt copy | compiler-rt move | fastmem baseline | Candidate C |
|---|---|---|---|---|
| 1 | 11 / 19 / 3 | 13 / 16 / 3 | 15 / 18 / 4 | 13 / 14 / 5 |
| 4 | 14 / 22 / 2 | 15 / 19 / 2 | 10 / 12 / 3 | 10 / 12 / 3 |
| 8 | 14 / 22 / 2 | 15 / 19 / 2 | 8 / 10 / 2 | 8 / 10 / 2 |
| 15 | 14 / 22 / 2 | 15 / 19 / 2 | 8 / 10 / 2 | 8 / 10 / 2 |
| 17 | 16 / 22 / 2 | 24 / 37 / 2 | 10 / 12 / 3 | 15 / 19 / 2 |

For one byte, fastmem performs three byte loads and three byte stores.
Its first store is at `0x1094b4e`.
Compiler-rt copy stores its first byte at `0x10ac9af`, before the middle and tail loads.
Compiler-rt move keeps all three loads before its first store at `0x10ac55f`.

Candidate C uses one byte load and store for one byte.
It uses a head/tail word pair for two or three bytes.
LLVM retains a zero-length test before its one-byte test, so the branch count increases.
The smaller instruction count does not establish a performance win.

For 17–63 bytes, C uses the existing overlap-safe four-XMM class from `compact.zig`.
This removes one size predicate but increases memory instructions.
The four loads precede all four stores, as the move contract requires.
The existing compiler-rt attribution in `THIRD_PARTY.md` covers this helper.

The instruction counts do not explain the aggregate c7a gap at 4–15 bytes.
Fastmem already executes fewer instructions there than either compiler-rt entry.
A front-end or call-site explanation remains unverified without target measurements.
C does not change the c7a set kernel.

## c7i: inline dispatch traverses unrelated vector classes

The baseline runtime copy loop is `bench_fastmem.runFastmemInline__anon_33150`, at `0x108d2f0`.
Its size dispatch starts at `0x108d3b6`.
For one byte, it tests the 256/64/32/16/8/4/2/1 boundaries before its first store at `0x108d4e3`.
The ABI entry at `0x1093590` instead uses three size predicates for one byte.
Neither short copy path executes vector cleanup.

Candidate C places the short decision before the inline vector ladder on Sapphire Rapids only.
It retains the original scalar operations and the configured inline threshold.
The new loop starts at `0x108d320`, with its first size decision at `0x108d3f4`.
The one-byte destination store is at `0x108d51a`.

| Length | Baseline inline predicates | C inline predicates | Baseline ABI predicates |
|---|---|---|---|
| 1 | 8 | 5 | 3 |
| 4 | 6 | 3 | 2 |
| 8 | 5 | 2 | 2 |
| 15 | 5 | 2 | 2 |

All 768 fixed-size copy/move/set probe bodies remain byte-identical to the baseline on Sapphire Rapids.
An initial compact-class prototype changed constant eight-byte copies and was removed before the fleet revisions.
The final implementation changes runtime dispatch, not constant-size memory operations.

## Reproduction

From the lane worktree, run these commands for a selected CPU and experiment:

```sh
nix develop "$PWD" -c zig build install -j1 \
  -Dtarget=x86_64-linux-gnu -Dcpu=znver4 -Doptimize=ReleaseFast \
  -Drev=baseline -Dx86-experiment=small_paths --prefix "$PWD/zig-out"
nix develop "$PWD" -c llvm-objdump -d --no-show-raw-insn \
  --x86-asm-syntax=intel "$PWD/zig-out/bin/bench-fastmem"
nix develop "$PWD" -c zig build codegen-x86 -j1 -Dx86-experiment=small_paths
```

The addresses above use `-Drev=baseline` and the default `-Dx86-variant=auto`.
Compiler-rt is the linked Zig implementation, not the dynamically resolved glibc implementation.
No glibc source or disassembly contributes to these changes.
